title: Context
description: What a run takes in, what it uses while it works, and what it returns.
---

A run starts with the bot's role, its offered skills, the forced skill's prompt, the triggering
event and what it may return. Three things add to that: preload before the run, notes and earlier
runs surfaced while it works, and hub tools it calls itself.

| Row         | What it holds                                                                |
| ----------- | ---------------------------------------------------------------------------- |
| **in**      | What the run looks at (`over`) and what it sees first (`preload`)            |
| **uses**    | Harness tools and hub tools                                                  |
| **returns** | The proposal kinds it may hand back; a check returns a verdict, pass or fail |

The studio shows these three rows for every job and check.

## Preload

`preload` renders context into the prompt before the run starts, through <Sym name="issueContext" />,
or switches on recall for it. Without `preload` a run gets `recall` alone.

| Value    | What it adds                                                            |
| -------- | ----------------------------------------------------------------------- |
| `issue`  | The triggering issue with its comments and the questions asked on it    |
| `links`  | Its parent, linked issues and sub-issues                                |
| `recall` | Notes and earlier runs surfaced by relevance while the bot works, below |

`recall` takes two settings: `cutoff`, the relevance a hit needs to be shown, and `budget`, how
much surfaced text one turn may add.

```yaml
preload: [issue, { recall: { cutoff: 0.5, budget: 1200 } }]
```

## Surfacing

Notes are what the hub knows, surfaced when relevant. A bot never lists the notes it reads. While
it works, the <Sym name="surfacer" /> plugin takes the task and each new turn, searches accepted
notes and the summaries of earlier runs, and adds the few that matter to the next model turn.

<Sym name="recall" /> ranks with BM25 first, then a small local model scores the top hits and drops those under the
cutoff. Proposed, superseded and retired notes are never surfaced.

Earlier runs are surfaced as far as the reading bot's `history` reaches: `none`, `run` (the same
job's earlier runs for the same event), `issue` (every run on the same issue), `bot` (the default,
its own runs) or `hub` (every run). The `history` tool reaches as far. After every run its events are written down
as one-line summaries (<Sym name="summarizeRun" />), extractive by default; `summarizer` on the bot
picks a model instead, or `off`.

The surfacer runs inside opencode. pi has no plugins, so a pi run gets no recall.

## Hub tools

`tools` on a bot, narrowed by a job, offers lookups a run calls when it needs them. They read; any
change goes through what the run [returns](/docs/proposals). opencode gets them from the bothub MCP
server (<Sym name="serveMcp" />); pi has no MCP client, so a pi bot gets preload but no hub tools.

| Tool                        | Reads                                                |
| --------------------------- | ---------------------------------------------------- |
| `issues_list`, `issues_get` | Issues, plans, specs and open questions              |
| `notes_search`, `notes_get` | Every note in the hub, with its status               |
| `runs_read`                 | Earlier runs from the run store                      |
| `history`                   | Summaries of earlier runs the bot may see, by search |

A run whose returns include `note` also gets `notes_add`, which proposes a note while it works.

```yaml
jobs:
  triage:
    type: bot
    bot: triager
    preload: [issue, links, recall]
    tools: [issues_get, notes_search]
```

## Sessions

`resume` says what a new attempt or run of a bot starts with besides its task. `none`, the default,
sends a retry only the failing check findings. `summary` adds a short summary of what the attempt
before did, and to a job that continues its work on an issue, what its last run did. `session`
continues the harness's own conversation: bothub copies the session out of the last run's home into
the new one, and opencode picks it up. A run with no session to hand over starts as with `summary`.
pi cannot continue a session yet, so a pi bot with `resume: session` does not load.

```yaml
resume: summary
history: issue
summarizer: extractive
```

## Issues

Issues go through one interface, <Sym name="Issues" />, with two backends picked in `hub.yaml`:

```yaml
issues: github # or local
```

`github` reads and writes real issues in the target repo (<Sym name="githubIssues" />). `local`
keeps them as files (<Sym name="localIssues" />), which is handy for trying a hub without touching
GitHub.

The code is on [Issues and context](/docs/reference/context).
