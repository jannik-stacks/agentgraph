---
title: Context
description: What a run knows before it starts, and what it can look up.
---

A run sees the bot's role, its offered skills, the notes it reads, the forced skill's prompt and
the triggering event. Beyond that there are two ways to give it more.

## Preload

`preload` renders context into the prompt before the run starts, through

<Sym name="issueContext" /> and <Sym name="relevantNotes" />. Use it for things every run of the job needs.

| Value   | What is rendered             |
| ------- | ---------------------------- |
| `issue` | The triggering issue         |
| `links` | Issues linked from it        |
| `notes` | The notes that match the run |

## Read-only tools

`tools` on a job offers lookups through the bothub MCP server (<Sym name="serveMcp" />), for things
a run might need. They
read, they never write; writing is what [proposals](/docs/proposals) are for.

| Tool                        | Reads                                   |
| --------------------------- | --------------------------------------- |
| `issues_list`, `issues_get` | Issues, plans, specs and open questions |
| `notes_search`, `notes_get` | Notes in the hub                        |
| `runs_read`                 | Earlier runs from the run store         |

```yaml
jobs:
  triage:
    type: bot
    bot: triager
    preload: [issue, links]
    tools: [issues_get, notes_search]
```

## Issues

Issues go through one interface, <Sym name="Issues" />, with two backends picked in `hub.yaml`:

```yaml
issues: github # or local
```

`github` reads and writes real issues in the target repo (<Sym name="githubIssues" />). `local`
keeps them as files (<Sym name="localIssues" />), which is handy for trying a hub without touching
GitHub. pi has no MCP client, so a pi bot gets preload but no tools.

The code is on [Issues and context](/docs/reference/context).
