## Serving

<Sym name="serveHub" /> is the local hub: it watches `issues/`, runs each change through the
[pipeline](/docs/reference/pipeline) one event at a time, plays GitHub's part with a local bare repository and serves
the read-only <Sym name="api" /> that BHM reads. <Sym name="serveGitHub" />
is the same for a GitHub App, with short-lived installation tokens that no bot ever holds.

Comments and new issues written while `serve` was stopped run when it starts again: each change
has a delivery id derived from its content, and the ones already delivered are skipped. On the
first start for a data directory, everything already in `issues/` is recorded as delivered
instead, so old `/bothub` comments do not run.

## Assignment and the queue

Work is assigned with a label. Adding `bot:implementor` to an issue emits an `issues` event with
action `labeled` and that label, one event per added label, the same shape a GitHub delivery
has. A workflow picks it up with a `labels` filter next to `types`:

```yaml
on:
  issues:
    types: [labeled]
    labels: [bot:implementor]
```

The `bot:` prefix is a convention, not a keyword: any label works, and the same workflow runs
unchanged on GitHub.

Each new event waits in a queue before it runs. <Sym name="fileQueue" /> keeps one JSON file per
item under `<data>/queue/`, named so they sort in push order. Taking an item renames its file to
carry the owning process, so two processes on one data directory never run the same item, and an
item a stopped process had taken goes back to waiting when the queue is next opened.

<Sym name="worker" /> runs items one after another.

Removing the label withdraws the work. Before an item runs, <Sym name="withdrawn" /> checks that
the label which started it is still on the issue and drops the item if not; a job already running
finishes. bothub adds no status labels of its own: waiting work is in the queue's `list`, and
once it starts, its runs carry their status and closure.

## Sim

`bothub sim <scenario>` runs a hub against a scripted human action. Bots are replaced by a scripted
harness and checks by scripts that pass or fail as told; dispatch, the pipeline, the MCP server,
validation and apply are real. <Sym name="simulate" /> runs one.
