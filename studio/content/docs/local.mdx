title: Running it locally
description: Commands to validate a hub, dry-run it and open BHM.

You need Node 22.18 or later. Commands run from the `bothub` directory unless noted.

## The CLI

```sh
bin/bothub.mjs check --dir examples/acme-app
bin/bothub.mjs plan --event issue_comment examples/payloads/issue-comment.json --dir examples/hub
bin/bothub.mjs run --event issue_comment examples/payloads/issue-comment.json --dir examples/hub --dry-run
bin/bothub.mjs runs
bin/bothub.mjs logs <run id> --follow
```

- `check` compiles a hub and prints every error, and warns about checks no job uses.
- `plan` shows which jobs a webhook payload would start.
- `run` runs them on this machine. `--dry-run` prints each agent session instead of starting it.
- `runs` lists runs, newest first, and `logs` prints a run's events.
- `schema` prints a JSON Schema for each file kind, handy for editor completion.
- `serve` watches a local hub's issues and runs what they start (<Sym name="serveHub" />), `sim`
  runs a scenario without a model (<Sym name="simulate" />) and `mcp` serves a hub's read tools.
  See [Events and serving](/docs/reference/serve).

Add `--json` to any of them for machine-readable output. `--data` points at a data directory
other than `$BOTHUB_DATA` or `~/.bothub`.

## BHM

From `studio/`:

```sh
npm install
npm run dev
npm run seed
```

`npm run dev` starts the API on port 5181 and the app on http://localhost:5182, pointed at the
acme-app example hub. Pass `-- --hub <dir> --data <dir>` to point it elsewhere. `npm run seed`
writes a few sample runs into the data directory so the Dashboard has something to show; add
`-- --live` to stream one slowly. The API restarts by itself when files under `src/` change. If it
runs code older than `src/` anyway, BHM shows a banner until the API catches up.

## Before you commit

Run `npm run verify` from the `bothub` directory. It stops at the first failure and runs, in order:

- `oxfmt --check` over `src`, `tests`, `bin` and `studio`. Test fixtures are left alone, since
  tests depend on their line numbers.
- `oxlint`, then `tsc --noEmit` for bothub and for studio.
- `vitest run --coverage` with the coverage thresholds. Besides the unit tests this checks that
  every API path studio fetches is served, every docs reference and docs link resolves, every
  route and studio tab has a nav entry, every example hub compiles, and every acme-app bot's
  model is served by LiteLLM and allowed by its key in `keys.sh`. The run fails if a test leaves
  a process running.
- The studio build, which fails on a docs reference to source that does not exist.
- `bothub check` on every hub under `examples/`.

## Editing the hub

The graph shows the flow. Each workflow file is a frame around its triggers, its jobs and the
checks that gate them, and the frame's title opens the file. A job is one step that casts a bot and
hands it a skill; both show on the job's card, and the Bots and skills layer draws them as their own
nodes under the steps that cast them. Notes are not nodes. Selecting a job or a bot lists what its
run starts with: the bot and the skill, what it takes in, what it uses and what it returns. Notes
are surfaced by relevance while the bot works, so no step lists them; the Notes tab lists every
note by kind, with its status and the check that enforces it.

Studio edits every kind of hub file: `hub.yaml`, bots, skills, checks, workflows, notes and local
issues. With no node selected, the side panel lists the hub's items by kind, each with a button to
add a new one. A selected node has an Edit button that opens the file behind it; for a job or a
trigger that is its workflow, with that job opened.

The form is built from the same schemas `bothub check` uses, so a field added to a file kind shows
up in studio without a change to studio. Lists of names offer the hub's skills, bots, checks, job
ids, tools and model aliases as chips, and a name that points at another item links to it. Each
workflow job is its own section: give it a bot and a skill or a `run` command, its `needs`, and the
checks it loops `until`. Renaming an item moves its file and updates every reference to it.

Edits stay pending until you save them. The tray under the graph shows a diff per file and the
whole hub is compiled again on every keystroke (<Sym name="validateHub" />); problems appear next to
the field they are about, and Save stays disabled until the hub compiles. The graph previews the
pending hub as you type.

Save writes through <Sym name="writeHub" />, which compiles the hub once more on the server and
writes nothing if it does not compile. It only writes item files inside the hub directory, refuses
symlinks and any file that changed on disk since studio loaded it, keeps comments and formatting of
fields that did not change, and answers only on localhost. When the hub directory is in a git work
tree, Save and commit also commits exactly the saved files as `update`. It never pushes.

## The model stack

From `infra/local`:

```sh
cp .env.example .env              # set LITELLM_MASTER_KEY and provider keys
ollama pull qwen3.5:4b
ollama pull tev1:0.8b
docker compose up -d              # LiteLLM and Postgres
docker compose --profile sandbox up -d
docker build -t bothub-sandbox:local sandbox
./keys.sh                         # one virtual key per bot, written to .keys.env
```

Copy the `BOTHUB_LLM_API_KEY_<BOT>` lines from `.keys.env` into `$BOTHUB_DATA/.env`, then point
bothub at the proxy with `BOTHUB_LLM_BASE_URL=http://127.0.0.1:4000`. The ChatGPT login for
`smart` and `writer` runs once from the CLI; `infra/local/README.md` has the steps.

`docker compose --profile sandbox --profile ollama --profile compute down` stops everything and
keeps the volumes.
