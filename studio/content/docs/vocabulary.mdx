| Word         | What it is                                                                              | Where it lives                            |
| ------------ | --------------------------------------------------------------------------------------- | ----------------------------------------- |
| **trigger**  | Something that happened: a GitHub event, a comment command, a schedule                  | `on:` in a workflow or job                |
| **bot**      | Who acts. Harness, model alias, tools, what it may write (`can`). Only bots run a model | `bots/<name>.md`, body is the role        |
| **skill**    | What to do. A prompt the job forces or the bot is offered                               | `skills/<name>.md`, body is the prompt    |
| **workflow** | A small graph from triggers to jobs                                                     | `workflows/<name>.md`                     |
| **job**      | One step in a workflow: it casts a bot and hands it a skill, or runs a plain script     | inside a workflow                         |
| **check**    | A script or a bot that returns a verdict, pass or fail with findings                    | `checks/<name>.md`                        |
| **branch**   | Where work happens. One worktree per run, never the default branch                      | runtime                                   |
| **proposal** | The only way a bot changes anything on GitHub                                           | runtime, see [Proposals](/docs/proposals) |
| **run**      | One bot or script executing one job attempt, with events, cost and an outcome           | the run store                             |
| **note**     | What the hub knows                                                                      | `notes/<kind>/<slug>.md`                  |

Each file kind has a schema; the fields are listed on [Schema and config](/docs/reference/config).

## Hierarchy

Everything sits under one of two roots. The repository is the top: whatever has to last is in
git, reviewed through pull requests. The data dir holds what runs produce. It is never in git; it
sits on local disk today and on S3-type object storage later.

```
repository (git)
  hub              hub.yaml, bots/, skills/, workflows/, checks/
    workflow       triggers and jobs
      job          a bot running a skill, or a script, gated by checks
  notes/           decisions, conventions, patterns, caveats
  issues           issues/*.md locally, GitHub issues in GitHub mode
  code             the default branch, bot branches, pull requests

data dir (not in git, object storage later)
  runs/<id>/       run.json, events.jsonl, outcome.json, memory.md
    home/          the harness's own sessions and transcripts
  queue, deliveries, locks
  repos/, work/    mirrors and worktrees, rebuilt when missing
```

Runs point up: each run records its repository, workflow, job and bot. Nothing in the data dir is
the source of truth. When something a run learned should last, it goes back into the repository
as a proposal: a note, an issue or a commit.

## Notes

There are four kinds of note, split into rules and knowledge.

- **decision** and **convention** are rules. A rule note with `paths` is always loaded when a run
  touches matching files. A decision changes only through a new decision that supersedes it.
- **pattern** and **caveat** are knowledge. A pattern is a reusable solution worth copying, a
  caveat is a known sharp edge in our own design. They load only when relevant.

Bots and skills choose which kinds they read with `notes: [decision, convention]`. A note can name
the `check` that enforces it, which is how a rule earns teeth (see the correction ladder in
[The loop](/docs/loop)). Which notes a run loads is decided by <Sym name="relevantNotes" />.

## Issues as the work queue

Some things look like notes but are not.

- An **open question** is an issue labelled `unsure`. A bot that is unsure asks instead of
  guessing, and a human answers in the thread, which is itself a trigger.
- A **plan** is an issue labelled `plan` with sub-issues for each step.
- A **spec** is an issue labelled `spec`.

## Memory

Memory is not one thing in bothub, and most of it sits outside the hub on purpose. Only notes are
reviewed and only notes are shared as rules.

| What               | Kept where                 | Who reads it                         |
| ------------------ | -------------------------- | ------------------------------------ |
| **note**           | `notes/` in the repository | every run it is relevant to, by rule |
| **run memory**     | `runs/<id>/memory.md`      | humans                               |
| **transcript**     | `runs/<id>/home/`          | humans only, for now                 |
| **harness memory** | the harness's own files    | nobody, it is wiped with the sandbox |

Run memory is a short record the runner writes after each run: tools used, checks that failed and
why, what was proposed and what landed. A retry does not read it; it gets the failing check findings
directly. A transcript is the full conversation of a run; bots cannot search or resume earlier
transcripts yet. Harnesses like opencode keep their own memory files; bothub starts every run from
a clean home, so nothing carries over that way.

When something a run learned should outlast it, the bot proposes a note and a human accepts it.
That is the only path from memory to what the hub knows.
